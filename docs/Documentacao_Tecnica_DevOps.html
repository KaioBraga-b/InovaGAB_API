CI — Integração Contínua (.github/workflows/ci.yml)

Disparado a cada push (qualquer branch) e pull request. Executa os testes com MongoDB real em service container do GitHub Actions.

#PassoDescrição
1CheckoutClona o código-fonte do repositório
2Setup Java 24Instala JDK Temurin com cache Maven
3Testes./mvnw -B test com MongoDB 7.0 em service container
4Package./mvnw -B -DskipTests package → gera .jar
5ArtifactPublica o .jar como artifact do GitHub Actions
6Docker BuildBuild da imagem Docker com Buildx + cache GHA
7Push GHCRPublica ghcr.io/kaiobraga-b/inovagab_api:<sha> + :latest

CD — Entrega Contínua (.github/workflows/cd.yml)

Disparado em push nas branches main e develop. Resolve o ambiente alvo automaticamente pela branch.

#PassoDescrição
1Resolve Ambientedevelop → staging / main → produção
2Build + PushConstrói e publica imagem no GHCR (tag por SHA)
3SSH AgentConfigura chave SSH para acesso ao servidor
4Deploy Remotoscripts/deploy-remote.sh → envia bundle via SSH
5Applyscripts/remote-apply.sh → docker compose pull && up -d
6HealthcheckValida /actuator/health retornando {"status":"UP"}

Seção 03

Docker — Containerização

Estratégia: Multi-Stage Build — separa o ambiente de compilação (JDK) do ambiente de execução (JRE), reduzindo a imagem final em ~60%.

Dockerfile (Multi-Stage)

📄 Dockerfile # ═════════════════════════════════════════════════════ # STAGE 1: BUILD # ═════════════════════════════════════════════════════ FROM eclipse-temurin:24-jdk AS builder WORKDIR /app COPY mvnw mvnw.cmd ./ COPY .mvn .mvn COPY pom.xml ./ RUN chmod +x mvnw && ./mvnw dependency:go-offline -B COPY src ./src RUN ./mvnw clean package -DskipTests -B # ═════════════════════════════════════════════════════ # STAGE 2: RUNTIME (imagem final leve) # ═════════════════════════════════════════════════════ FROM eclipse-temurin:24-jre WORKDIR /app RUN groupadd -r appuser && useradd -r -g appuser appuser COPY --from=builder /app/target/*.jar app.jar EXPOSE 8080 ENV SPRING_PROFILES_ACTIVE=production HEALTHCHECK --interval=30s --timeout=10s --retries=3 \ CMD curl -f http://localhost:8080/actuator/health USER appuser ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

Práticas de Segurança

🔒 Usuário Não-Root

Container executa como appuser, não como root. Reduz superfície de ataque.

📦 Multi-Stage Build

Imagem final contém apenas JRE + JAR. Sem JDK, Maven ou código-fonte.

💓 Healthcheck Nativo

Docker monitora /actuator/health a cada 30s. Container reinicia se falhar.

🚫 .dockerignore

Exclui .git, target/, .env e docs do contexto de build.

Comandos Docker Utilizados

📄 Comandos Docker # Build da imagem $ docker build -t inovagab-api:latest . # Rodar container isolado $ docker run -p 8080:8080 --env-file .env inovagab-api:latest # Subir todos os serviços (API + MongoDB) $ docker compose up -d --build # Verificar containers $ docker compose ps # Ver logs da aplicação $ docker compose logs -f api # Parar tudo $ docker compose down # Limpar tudo (containers + volumes + imagens) $ docker compose down -v --rmi all

Orquestração com Docker Compose

Três configurações Docker Compose isoladas: desenvolvimento, staging e produção — cada uma com banco, rede e volume próprios.

Três Ambientes Isolados

AmbienteArquivo ComposePortaBancoProfileBranch
Dev docker-compose.yml 8080 inovagab_db local qualquer
Staging deploy/staging/docker-compose.yml 8081 cidades_esg_staging staging develop
Produção deploy/production/docker-compose.yml 8080 cidades_esg prod main

Recursos do Docker Compose

🔗 Networks

Rede bridge isolada (inovagab-network) permite comunicação entre containers pelo nome do serviço, sem expor portas desnecessárias.

💾 Volumes

Volume nomeado mongo_data persiste dados do MongoDB. Dados não são perdidos ao reiniciar containers.

🔐 Variáveis de Ambiente

Credenciais parametrizadas via .env / .env.example. Nenhuma senha hardcoded no compose.

💓 Healthchecks

depends_on: condition: service_healthy garante que a API só inicia após o MongoDB estar saudável.

Subindo os Ambientes

Seção 06

Desafios e Soluções

Todos os desafios abaixo ocorreram de fato durante a implementação do pipeline DevOps.

1. Compilação quebrada por BOM (Byte Order Mark)
3 arquivos Java (InovacaoController.java, InovacaoService.java, IdeiaRepository.java) continham BOM (\ufeff) no início, fazendo o javac falhar com illegal character: '\ufeff'.
✅ Solução: Removido com perl -pi -e 's/^\xef\xbb\xbf//' nos 3 arquivos. Build voltou a compilar normalmente.
2. MongoDB latest incompatível com kernel Docker
Erro: MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility. O container saía imediatamente ao iniciar.
✅ Solução: Pinado mongo:7.0 (versão compatível) em todos os ambientes (compose raiz e deploys). Validado com execução real.
3. Credenciais fixas no código-fonte
application.properties e application.yml traziam credenciais (root/secret) e JWT_SECRET hardcoded.
✅ Solução: Todas as credenciais migradas para variáveis de ambiente (${VAR:default}). Criado .env.example, profiles local/staging/prod e adicionado .env ao .gitignore.
4. Healthcheck bloqueado pelo Spring Security
/actuator/health retornava 403 Forbidden porque o Spring Security exigia autenticação para todos os endpoints.
✅ Solução: Liberado /actuator/health/** no SecurityConfig e expostos endpoints health,info no Actuator. Agora retorna 200 {"status":"UP"}.
5. Interpolação YAML do Compose quebrando
A mensagem ${IMAGE:?Ex.: ghcr.io/...} continha : interpretado como mapeamento YAML: mapping values are not allowed in this context.
✅ Solução: Valores de image: colocados entre aspas ("${IMAGE:?...}"). Validado com docker compose config.
6. Testes de integração exigem MongoDB ativo
./mvnw test falha sem MongoDB rodando em localhost:27017 — comportamento esperado dos testes de integração com @SpringBootTest.
✅ Solução: Documentado que mvn test requer o banco (docker compose up -d mongodb). No CI, o MongoDB é iniciado automaticamente como service container do GitHub Actions.
